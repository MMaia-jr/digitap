## 3. Modelo relacional candidato

### 3.1 Convenções comuns e fronteira de acesso

São propostas **seis tabelas novas**. Elas preservam as nove existentes. Todas recebem RLS habilitado, nenhuma policy para PUBLIC/anon/authenticated e nenhum grant de cliente; acesso somente pelo backend já autorizado, com permissões necessárias explicitamente revisadas. Acesso individual, inclusive a lista de vínculos e atestantes, permanece restrito.

UUIDs identificam entidades; `timestamptz` registra instantes do banco; datas são exibidas em America/Sao_Paulo. PKs e campos obrigatórios das tabelas novas podem ser NOT NULL. A proibição de NOT NULL prematuro refere-se às mudanças incompatíveis nas tabelas existentes e a `atividades.sujeito_id` durante EXPAND.

Salvo indicação contrária, FKs usam RESTRICT/NO ACTION, sem exclusão em cascata de histórico. Versões materiais não são sobrescritas; transições de situação e troca de apontadores correntes são auditadas. `eventos_editoriais` continua registrando autor, data, ação, anterior/novo e metadados restritos necessários. A coluna `objeto_tipo` existente não tem enum fechado, permitindo novos tipos auditáveis sem migration histórica.

A idade mínima e o histórico não serão CHECKs que dependem de `now()`: condições temporais e entre várias linhas são reavaliadas na transação de cada operação. Índices não terão predicados móveis de tempo; usarão colunas de instante e filtros de estado estáveis.

### 3.2 `sujeitos_publicadores`

| Coluna | Tipo / nulabilidade / significado |
|---|---|
| `id` | uuid PK, gerado no banco |
| `tipo` | text obrigatório, CHECK em pessoa_fisica/coletivo_informal/organizacao |
| `organizacao_legada_id` | uuid NULL, FK → organizacoes.id; UNIQUE quando preenchido |
| `nome_publico` | text obrigatório, NFC e trim; CHECK comprimento 2–160; texto sem HTML validado no servidor |
| `estado` | text obrigatório, default pendente; CHECK pendente/ativo/suspenso/encerrado |
| `modo_publicacao` | text obrigatório, default curadoria_previa; CHECK curadoria_previa/autopublicacao |
| `risco` | text obrigatório, default medio; CHECK baixo/medio/alto |
| `versao` | integer obrigatório, default 1; CHECK > 0; concorrência de estado/curadoria |
| `criado_por_conta_id` | uuid NULL, FK → contas_acesso.id; NULL só para origem legada documentada |
| `origem` | text obrigatório, CHECK legado/cadastro |
| `criada_em`, `atualizada_em` | timestamptz obrigatórios, banco |

Restrições:

- UNIQUE `(id,tipo)` para referências tipadas.
- Equivalência por CHECK: `tipo='organizacao'` se e somente se `organizacao_legada_id IS NOT NULL`.
- CHECK `risco='alto'` implica `modo_publicacao='curadoria_previa'`; suspensão efetiva não depende apenas desse campo.
- CHECK origem=cadastro exige criador; origem=legado exige tipo organização. Tipo e associação à organização tornam-se imutáveis após criação.
- Nome do sujeito organização não substitui o nome em snapshot já publicado; sincronização futura com organizacoes.nome_publico será explícita e auditada.

Índices: UNIQUE de organização legada; `(estado,risco)`; `(criado_por_conta_id)`; PK/UNIQUE tipado já cobrem a busca de subtipo. Não criar índice de enum isolado sem consulta que o justifique.

`estado`, `modo_publicacao` e `risco` são estado operacional/limite concedido, não prova suficiente de autorização. A permissão efetiva intersecta conta, vínculo, atestações, histórico, sanções, casos e autorização do conteúdo no instante da operação.

### 3.5 `vinculos_publicadores`

| Coluna | Tipo / regra |
|---|---|
| `id` | uuid lógico obrigatório, estável entre versões |
| `versao` | integer obrigatório > 0 |
| `atual` | boolean obrigatório default true |
| `sujeito_id` | uuid obrigatório, FK → sujeitos_publicadores.id |
| `conta_id` | uuid obrigatório, FK → contas_acesso.id |
| `papel_vinculo` | text obrigatório, CHECK titular/representante/membro |
| `escopos` | text[] obrigatório não vazio; CHECK por função imutável de array, sem consultas a tabelas, valida subconjunto de ler_privado/editar/enviar/publicar/gerir_vinculo e ausência de valores nulos/duplicados |
| `situacao` | text obrigatório, CHECK pendente/ativo/suspenso/revogado; default pendente |
| `origem` | text obrigatório, CHECK legado/cadastro |
| `revisao_validacao` | integer obrigatório default 1, CHECK > 0 |
| `atestacao_1_id`, `atestacao_2_id` | uuid NULL, ambas presentes ou ambas ausentes; distintas quando preenchidas |
| `curadoria_caso_id`, `curadoria_caso_versao` | uuid/integer NULL coerentes |
| `criada_em`, `atualizada_em` | timestamptz obrigatórios |
| `ativada_em`, `suspensa_em`, `revogada_em` | timestamptz NULL; CHECKs de coerência com a situação |

PK `(id,versao)`; UNIQUE `(id,versao,sujeito_id)`; UNIQUE parcial `(id) WHERE atual`; UNIQUE parcial `(conta_id,sujeito_id) WHERE atual`. Isso representa N:N sem dois vínculos correntes ambíguos para o mesmo par. A identidade `(conta_id,sujeito_id)` de um id lógico é imutável entre versões, garantida por trigger; troca de representante usa outro id lógico, revogando o anterior. A mudança de papel/escopos cria nova versão material; a anterior permanece, marcada não atual.

FK de curadoria inclui sujeito. Cada apontador de atestação usa FK `(atestacao_N_id,id,versao) → atestacoes_representacao(id,vinculo_id,versao_vinculo)`, deferrable para a construção transacional dos registros relacionados.

Índices: `(sujeito_id,atual,situacao)`, `(conta_id,atual,situacao)`, cada apontador de atestação, chave de curadoria. As chaves parciais não substituem os índices completos usados por FKs históricas.

Integridade entre tabelas:

- Titular PF deve coincidir com pessoas_fisicas.conta_id; não se obtém papel editorial por esse vínculo.
- Representante de coletivo só ativa com duas atestações designadas válidas e decisão editorial. Vínculo de membro não concede publicação por default e não exige duas atestações para poder apenas declarar pertencimento.
- Representante de organização legada conserva somente o acesso que o vínculo antigo e a conta ativa já concediam; não recebe escopos institucionais presumidos.
- Só conceder escopos por operação autorizada. Detentor de publicar não ganha gerir_vinculo; delegação administrativa não está implicitamente aberta.
- Ativar, suspender, revogar ou trocar atestações correntes é transação auditada. Os eventos preservam versão, revisao_validacao e IDs das atestações anteriores/novas.

### 3.6 `atestacoes_representacao`

| Coluna | Tipo / regra |
|---|---|
| `id` | uuid PK |
| `vinculo_id`, `versao_vinculo` | uuid/integer obrigatórios, FK composta → vinculos_publicadores(id,versao) |
| `posicao` | smallint obrigatório, CHECK 1 ou 2 |
| `atestante_conta_id` | uuid obrigatório, FK → contas_acesso.id |
| `declara_membro` | boolean obrigatório, CHECK true |
| `declara_pessoa_distinta` | boolean obrigatório, CHECK true; declaração a ser examinada humanamente |
| `situacao` | text obrigatório, default vigente; CHECK vigente/revogada/substituida |
| `atestada_em` | timestamptz obrigatório do banco |
| `revogada_em` | timestamptz NULL; obrigatório para revogada |
| `pedido_id` | uuid obrigatório |
| `payload_sha256` | text obrigatório, CHECK 64 caracteres hexadecimais |

UNIQUE `(id,vinculo_id,versao_vinculo)`; UNIQUE `(atestante_conta_id,pedido_id)`; UNIQUE parcial `(vinculo_id,versao_vinculo,posicao) WHERE situacao='vigente'`; UNIQUE parcial `(vinculo_id,versao_vinculo,atestante_conta_id) WHERE situacao='vigente'`.

Índices: chave do vínculo, `(atestante_conta_id,situacao)`; índices completos para os apontadores inversos já cobertos pelo UNIQUE triplo.

A transação de atestar revalida conta ativa, idade, pertencimento declarado, tipo coletivo do sujeito e vínculo exato. A idade mínima volta a ser verificada na ativação/publicação. Conta diferente é verificável; pessoa civil diferente não é garantida por duas contas. Curadoria não pode apresentar essa limitação como prova civil ou autorização institucional.

Revogação de uma atestação designada suspende **o vínculo afetado** na mesma transação e audita; não apaga contribuições passadas. Vínculo materialmente alterado não reutiliza atestação de versão anterior. Na reatestação sem mudança de representante/escopos, proposta técnica: manter a versão material e a outra atestação ainda válida, substituir o apontador revogado por uma nova atestação da mesma posição e incrementar revisao_validacao; registrar todo o histórico no evento. Reativação exige nova verificação editorial, sem restauração automática por cron ou retry antigo. Esse procedimento deve ser aprovado na revisão do plano.

Cada nova versão exige incremento monotônico e uma transição permitida; versão anterior e sua decisão ficam preservadas. Atualização do marcador atual é controlada transacionalmente.

CHECKs de alvo: sujeito exige atividade/registro nulos; atividade exige atividade não nula e registro nulo; registro exige ambos não nulos. FK `(atividade_id,sujeito_id) → atividades(id,sujeito_id)`; FK `(registro_id,atividade_id) → registros_realizacao(id,atividade_id)`; a primeira exige UNIQUE aditivo em atividades(id,sujeito_id), a segunda UNIQUE aditivo em registros_realizacao(id,atividade_id). FK `(caso_origem_id,caso_origem_versao,sujeito_id)` aponta para a versão decidida original. Trigger impede origem no próprio caso, ciclo, origem de outro sujeito e origem ainda não decidida. A contestação é um caso próprio e não reescreve a decisão original.

CHECKs: resultado/decisor/data obrigatórios em estados terminais; procedente implica resultado procedente; improcedente implica resultado improcedente; encerrado pode ter sem_julgamento, sem apagar decisão antecedente. Datas coerentes; prazo de recurso igual a `decidida_em + 30 dias`. Notificação não desloca o marco. Sanção exige decisão editorial e os campos condicionais da taxonomia acima; contestação factual C08 permanece sem prazo.

Índices: `(sujeito_id,atual,estado)`, `(sujeito_id,decidida_em)` filtrado por resultado procedente, `(atividade_id)`, `(registro_id,atividade_id)`, chave de origem; índices individuais de contas autora/analista/decisora. Fila corrente por `(estado,aberto_em) WHERE atual`.

Transições candidatas seguem I4-D9 literalmente: aberto → em_analise → procedente/improcedente/encerrado. Não há transição terminal de volta a aberto nem troca silenciosa de veredito. Reanálise/contestação abre outro caso relacionado; ação de reforma exige efeito explícito, prova e aprovação do procedimento. Encerrar um recurso não elimina sanção do caso original por simples contagem do estado atual.

### 3.8 Controle de subtipo e integridade além de FKs

**Escolha proposta:** FK composta com discriminador constante nos subtipos, combinada com constraint triggers adiáveis para completude. Um CHECK da linha filha fixa o discriminador; a FK tipada impede pessoa_fisica apontar para coletivo ou organização. A PK da filha impede duas linhas de PF para o mesmo sujeito; UNIQUE conta_id garante a cardinalidade PF/conta.

As FKs garantem o sentido filho → pai; não garantem que todo pai PF/coletivo tenha sua filha. Constraint triggers ao final da transação, nos pais/filhas, verificam exatamente uma filha do tipo correspondente. Para organização, o CHECK/FK organizacao_legada_id no pai é o subtipo. Tipo do sujeito e identidade material são imutáveis; exclusão deixa de ser opção enquanto houver vínculos/conteúdo/histórico. Não há órfão visível entre commits. Todas as criações de pai+filha ocorrem na mesma transação.

CHECKs não serão usados como consultas disfarçadas a outras tabelas. As referências tipadas são a primeira barreira; triggers ficam limitados a completude, temporalidade, transições e coerência entre relações. Funções propostas: SECURITY INVOKER, search_path fechado, sem EXECUTE de cliente nem SECURITY DEFINER como atalho. As condições são verificadas também pelo serviço para mensagens úteis, sem depender exclusivamente dele.

## 4. Permissão efetiva, histórico e moderação

### 4.1 “Em nome de quem?” e isolamento

A interface lista apenas vínculos próprios elegíveis e exige seleção explícita ao publicar. O sujeito escolhido é um **seletor**, não uma autorização: backend confere conta de Auth verificada, situação, vínculo atual/versão/escopos, sujeito, atestações, risco e autorização do objeto. Sessão não guarda aprovação permanente para um sujeito; seleção de outra aba/dispositivo não muda a titularidade de um pedido já preparado.

Também definir sujeito na criação do rascunho, para haver titular e isolamento desde o início. A pergunta volta na publicação como confirmação. Troca de titular de um rascunho ou de atividade publicada não está autorizada neste plano; escolher outro sujeito cria outro rascunho. O sujeito de uma atividade publicada é imutável. I4-D5 não autoriza transferência.

Conta editorial que também possui vínculo atua em contexto explícito: publicar como titular e decidir como editor são operações diferentes e auditadas. A regra de impedimento por conflito de interesse precisa de decisão humana; não presumir nem autorizar autoaprovação institucional por existir vínculo.

### 4.2 Regra I4-D6 como predicado reavaliado

Proposta de cálculo auditável, sem score de reputação:

1. Contar atividades distintas do mesmo sujeito, nunca cliques, versões, republicações ou quantidade de representantes.
2. Usar o primeiro evento de publicação válido de cada atividade para o relógio do histórico; propor janela inclusiva `[t-365 dias,t]` e primeira entre as elegíveis `<= t-30 dias`. Confirmar essa leitura na revisão do plano. Repetir publicação não reinicia idade nem cria uma quarta atividade.
3. Excluir atividade com infração procedente atribuída a ela. Consultar decisões/sanções preservadas, incluindo casos originais com recurso; mudança de estado para encerrado não zera antecedentes.
4. Exigir zero sanções procedentes do sujeito em `[t-180 dias,t]`. Janela móvel é recalculada na operação, sem CHECK temporal nem cache que conceda permissão sozinho.
5. Alternativa: pelo menos uma atividade elegível, seis meses calendários de conta, curadoria explícita referenciando sujeito+conta+vínculo. Propor idade a partir de contas_acesso.criada_em, sem trocar por 180 dias ou data de login. A conta invocante deve cumprir seus próprios seis meses; não há transferência entre contas do coletivo, conforme gate 4.
6. Em ambas as rotas, conta/vínculo vigentes, atestações necessárias e ausência de bloqueio por risco alto continuam obrigatórios. A exceção não apaga sanção, não resolve contestação e não concede papel editorial.

Não converter atestação, declaração de realização ou histórico de outro sujeito em prova de atividade. O instante de avaliação é do banco e é registrado no evento junto à versão da política e IDs de base, sem expor esse histórico individual publicamente.

### 4.3 Risco e alcance da suspensão

Proposta técnica: novos PF/coletivos começam em médio/curadoria_previa; organização pendente também não ganha publicação. Histórico elegível mais decisão/regras aprovadas habilitam baixo/autopublicacao. Nenhum backfill concede modo automaticamente.

Denúncia recebida abre caso e reabre curadoria; não se presume procedência. Denúncia procedente ou conteúdo contestado é alto no alcance afetado e suspende publicação até revisão. Casos com alvo conteúdo não suspendem outros sujeitos por associação. Alcance de suspensão de todo o sujeito e propagação a outras atividades exigem fundamento e decisão explícitos.

D7 e C08 seguem a política versionada aprovada: atividades legadas conservam política `i3` e relato público com marcador de contestação; atividades novas I4 usam política `i4`, com suspensão do alcance afetado por denúncia procedente. O versionamento preserva hashes e permite demonstrar os contratos de cada percurso, sem aplicação retroativa ao legado.

### 4.4 Atomicidade e concorrência

Proposta de protocolo único para caminhos I4: verificar Auth fora da transação; fazer pré-leitura apenas para descobrir o conjunto de alvos, sem conceder permissão; bloquear todas as contas relevantes (autora, representantes e atestantes) em ordem de UUID, em modo compatível com a mutação; depois sujeitos por UUID, vínculos por `(id,versao)`, atestações por UUID, casos, atividade, registro e autorização do objeto. Revalidar conteúdo e situação após os locks. Se o conjunto de contas/alvos mudou, abortar e reiniciar de forma limitada; não adquirir chave menor fora da ordem já iniciada. Bloqueio/desativação de conta participa do mesmo protocolo. Quando uma operação antiga já tiver locks em outra ordem, adaptar seu wrapper antes de permitir cruzamento com I4. Não ativar leitores/escritores mistos com ordens incompatíveis.

Publicação e revogação disputam o mesmo lock do sujeito/vínculo afetado. Revogação de atestação bloqueia vínculo e a autorização efetiva no mesmo commit; pedidos iniciados antes voltam a conferir versão/revisao_validacao após o lock. Revogação de autorização de conteúdo mantém o lock da atividade e a auditoria. Denúncia/decisão, suspensão, modo e evento são atômicos. Leitura pública verifica estado/moderação do sujeito e autorizações atuais do objeto sem cache, mesmo que o snapshot seja preservado. Revogar vínculo de representante impede ações futuras; não revoga automaticamente a autorização própria de conteúdo já publicado nem exige que o autor histórico continue representante. Suspensão de visibilidade histórica depende do alcance da decisão/moderação ou da revogação da autorização correspondente; não se transfere titularidade nem se apaga autoria.

Não fazer autorização crítica por chamadas HTTP separadas como se fossem uma transação. Não criar função privilegiada acessível a anon/authenticated. Retry preserva chave/contexto e revalida permissões atuais; mudança de sujeito/payload/ator conflita. SQL direto do backend continua sujeito às FKs/CHECKs/triggers; bypass de RLS não dispensa verificação de conta e objeto.

## 8. Rollback e preservação de dados

| Momento | Recuperação funcional | Estrutura e dados |
|---|---|---|
| EXPAND, sem novas gravações | Caminho legado; flags fechadas | Deixar adições inertes; remover só após prova de vazio e autorização específica |
| BACKFILL | Legado continua usando organizacao_id | Manter mapa/IDs; compensar lote identificado apenas se necessário e sem referências posteriores |
| COMPAT, só organizações | Desligar novo consumo e voltar a escritor legado compatível | Manter esquema/dual data/diário; não apagar auditoria |
| CUTOVER, antes da primeira atividade PF/coletivo | Congelar abertura e voltar ao caminho organizacional, conforme checklist e backup | Preservar objetos de cadastro/atestação; não presumir que são descartáveis |
| CUTOVER, após conteúdo PF/coletivo | Release de recuperação lê sujeitos; novas escritas/autopublicação bloqueadas | Não reinstalar NOT NULL de organizacao_id; preservar conteúdo, autoria, atestações, casos e snapshots |
| CONTRACT futura | Exige plano novo | Não definida; nenhuma remoção aprovada |

“Sem perda” exige prova de restauração e comparação, não apenas um dump produzido. Backup e restauração têm destino isolado aprovado; não sobrescrever banco corrente com cópia antiga e perder ações posteriores. Migration compensatória futura segue o mesmo processo de revisão/CLI; migrations históricas não são apagadas/editadas. Voltar código não equivale a poder voltar schema após novos tipos de dados.
